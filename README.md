# LINE → Slack → Dots 中継

個人のLINE公式アカウント「Dots」（`@638fnwlr`）から、Slackの `#チャンネル-サンプル` にメンションを送り、Dotsのスレッド返信をLINEへ返します。登録したLINEユーザー1人からのテキストと画像を受け付けます。

## 公開先

- Worker: https://line-dots-bridge.line-dots-bridge.workers.dev
- ヘルスチェック: `/health`
- LINE Webhook: `/line`
- Slack Events API: `/slack`

Cloudflare WorkersとSQLite Durable Objectで動作します。PCを起動しておく必要はありません。返信の生成はSlackに接続したDotsへ依頼し、会話の振り分けにはOpenAI Decisions APIを使用します。Cloudflare・LINEの利用上限に加え、分類にはOpenAI APIの料金が発生します。

## Decisions APIによる自動振り分け（公開済み）

通常送信をOpenAI Decisions API（`gpt-6-luna`）で既存スレッド・`NEW`・`CLARIFY`へ分類します。分類には登録済みスレッドの原文ログと画像、機能公開後のLINE送受信順を使用します。分類の指示・他スレッドの情報・判定結果はDotsへ投稿しません。LINEの引用返信は保存済みの対応を優先し、API判定を省きます。会話候補が0件の場合もAPIを呼びません。

`CLARIFY`では送信を保留し、LINEに送信先の選択カードを表示します。カードは後続メッセージで消えないFlex Messageで、候補のページ切り替え・新規会話・送信のキャンセルに対応します。本人からの署名検証済みポストバックと保存済み候補が一致した場合だけ、保留した原文を1回投稿します。APIエラーや不正な分類結果から投稿先を推測する処理はありません。

既存スレッドの履歴は初回のみページ単位で取り込み、以後はSlackイベントで更新します。履歴の取り込みでは古い返信をLINEへ再送しません。移行前のLINE画面上の送受信順は保存されていないため、推測による復元は行いません。文脈だけで対象を特定できない短い参照は`CLARIFY`の対象です。

画像はSlackの非公開ファイルから読み込み、インライン画像としてDecisionsへ渡します。画像の再圧縮・DBへのバイナリ保存・公開URL化は行いません。新着画像のダウンロードは転送と分類で共有し、同じバイト列の画像証拠はSHA-256でまとめます。Workerのメモリ使用を制限するため、分類1回の画像証拠は重複排除後の合計10 MiBまでです。上限を超えた場合は明示的な配信失敗として記録します。

`OPENAI_API_KEY`はユーザーが承認した`../../work/line-dots.env`へ、新規キー`line-dots-bridge-routing`として保存し、Worker Secretへ反映済みです。値はGitやチャットに出力しません。Slackの`files:read`は、テストチャンネル外の非公開ファイルにも及ぶことを説明して明示承認を得た後、追加・再インストール済みです。本人のユーザーID・ワークスペースID・権限と、非公開JPEGのHTTP 200での取得を確認しています。中継コードの対象は設定済みチャンネルの登録済み会話に制限します。

2026年10月16日の確認結果は、自動テスト54件成功、workerd上で画像文脈の分類→既存スレッドへの投稿成功、LINE公式メッセージ検証APIで選択カード成功です。実際のDecisions APIによる架空の日本語15ケースは全件期待どおりでした。実運用の精度を保証する結果ではありません。

## 設定済みの外部サービス

## 配信と障害の確認

LINEとSlackの署名を検証し、受信イベントを永続キューに保存してから直ちに応答します。実際の配信はDurable ObjectのAlarmで処理します。同じイベントIDは重複送信しません。

Dotsの返信はSlackの表示用`rich_text`ブロックからLINE向けテキストへ変換します。通知用のトップレベル`text`では段落が空白に置き換わる返信があったためです。段落内の改行・空行、箇条書きの項目と番号、引用・コード内の改行を保持し、リンクはラベルとURLを送ります。表示ブロックを持たない通常のテキストメッセージは本文をそのまま使用します。未知のブロックや要素は種類を明示してエラーにし、通知用本文への切り替えで欠落を隠しません。追加のAI呼び出しや外部API呼び出しはありません。

改行修正の公開版は`9477873a-a3cf-46ff-8c83-ade2a85b317a`です。実際の返信データで改行0個の通知用本文から表示用データの改行5個・3段落を復元することを確認しました。回帰テストとworkerd統合テストを含む自動テスト61件が成功しています。

本番のテストスレッドでDotsへ段落・行内改行・箇条書きの返信を依頼し、返信`1792133288.832929`で6個の改行を保持することを確認しました。LINE送信ジョブ`slack:Ev0C9L5GKYJZ:0`は`delivery_done`です。実端末での表示は未確認です。

- LINEで通常送信：Decisions APIで既存の会話への続きか、新しい会話かを分類します。特定できない場合はLINEの選択カードで確認します。
- LINEでDotsのメッセージを長押しして［リプライ］：そのメッセージに対応するSlackスレッドへ送信します。別の会話を始めた後でも、元の会話を継続できます。

LINE送信APIが返す `sentMessages[].id` とSlackスレッドを永続保存し、Webhookの `quotedMessageId` で返信先を照合します。どちらの検索も主キーを使います。長文を分割した場合も各メッセージIDを保存します。既存の単一スレッドは移行時に保持し、新しく届くDots返信をLINEへ返します。

変更前にLINEへ送信済みのメッセージIDは保存されていないため、そこへの引用返信は対応先を特定できません。対応情報のない引用返信は `Unknown LINE quoted message` として配信失敗を記録し、Slackには投稿しません。変更後に届いたDotsの返信へリプライしてください。

```sh
npx wrangler tail --format pretty
```

配信完了は `delivery_done`、失敗は `delivery_failed` とジョブID・原因を記録します。HTTP 200のWebhook応答だけでは外部への配信完了を意味しません。メッセージ本文とトークンをアプリログに出力しません。

外部APIのタイムアウトなど、送信済みか判断できない失敗は自動再送しません。キューの `failed` / `sending` 状態を残します。Slackの実際の投稿を確認したうえで再送の要否を判断してください。再起動後もスレッドとキューは保持されます。

## LINEからの画像送信

LINEに送ったJPEG・PNG・GIF・WebP画像を、元のバイト列のままSlackの非公開チャンネルへ添付します。上限は1枚10 MiBです。画像の再圧縮・変換は行わず、CloudflareのDBには画像IDと配信状態だけを保存します。画像本体は転送中だけメモリに保持し、読み込み上限を超えた時点で取得を中止します。

通常の画像送信もDecisions APIで投稿先を分類します。新規会話なら、画像とDotsへのメンションだけを1つの親投稿にまとめます。「画像」だけの仮の親投稿や固定の依頼文は付けません。`files.completeUploadExternal` の `initial_comment` にメンションを指定し、画像と同時に共有します。既存会話と判定した画像や引用返信の画像は、対応するスレッドに画像とメンションをまとめて投稿します。複数枚を送った場合は1枚ずつ分類します。

添付確定APIは親投稿のタイムスタンプを返さないため、アップロードしたファイルIDを保存し、署名検証済みのSlackメッセージイベントに含まれる同じIDでスレッドを登録します。別のファイルやチャンネルは登録しません。Dotsの返信イベントが先に届いた場合も、対応するスレッドが登録されるまで `waiting_thread` として保持し、その後LINEへ返します。推測で返信先を選んだり、Slackをポーリングしたりする処理はありません。画像1枚あたりの外部HTTP呼び出しは6回から4回に減っています。

2026年10月16日にSlack CLIで認証し、既存マニフェストにUser OAuth権限 `files:write` を追加しました。CLIと同じ再インストールAPIで反映し、本人のユーザーID・ワークスペースIDと、発行されたユーザートークンの権限を `auth.test` で確認済みです。更新したトークンをWorker Secretsへ登録しています。

初回の実画像送信は、Slackの `files.getUploadURLExternal` がJSON本文の `filename`・`length` を未指定として扱い、`invalid_arguments` で失敗しました。フォーム形式で成功することを実APIで確認し、形式を検証する回帰テストを追加して修正しました。添付確定APIはJSON形式で受理されることを確認済みです。

再送時にはworkerdが `redirect: 'error'` をサポートしないことが判明しました。`manual` に変更してHTTP 200以外は拒否し、転送先へのリダイレクトに追従しない方針を保っています。回帰テストとworkerdの統合テストを追加しました。

画像の単一親投稿を導入した時点の公開版は `ffa055a3-6160-4c48-863a-2cbed78d08d2` でした。親投稿に画像とメンションをまとめた実APIの確認では、Dotsが画像内の「109シネマズ木場」を正しく読み取り、同じスレッドへ返信しました。固定文を省いた当時の公開版でも、受信済みの画像を中継経路へ1回再投入し、親投稿 `1792125251.598219` の本文がメンションのみで画像ファイルが同居していることを確認しました。約35秒後にDotsが「画像、こちらでも見えています。」と返信し、対応するLINE送信ジョブ `slack:Ev0C9QEP53T4:0` の `delivery_done` まで確認済みです。

ファイルを公開URLに変換する処理はありません。LINE上の保存期限切れ、サイズ上限超過、権限不足などは `delivery_failed` と原因を記録します。

## 対応範囲

- LINEの個人トークからのテキスト・画像送信
- Dotsによる、対応するSlackスレッド内の新規テキスト返信
- LINEの文字数上限を超える回答の分割

10 MiBを超える画像、外部URLを使う画像プロバイダー、ファイル・音声・グループトーク、Slack上の既存返信の編集反映は対象外です。メッセージと配信状態はDurable Objectに保存されます。

返信先の識別仕様は、LINE公式の[引用メッセージの受信](https://developers.line.biz/ja/docs/messaging-api/receiving-messages/#receive-quote-messages)と[送信時のメッセージID取得](https://developers.line.biz/ja/docs/messaging-api/get-quote-tokens/#get-quote-tokens-in-response)に基づいています。
